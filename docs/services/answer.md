# answer

Собирает контекст через `retrieval` и генерирует ответ с цитатами. Поддерживает
вопрос по базе и вопрос по приложенному файлу.

## Ответственность

- `POST /api/v1/answers` — ответ по базе знаний; создаёт диалог, пишет реплику,
  ответ и цитаты.
- `POST /api/v1/answers/file` — ответ по загруженному файлу (файл живёт только
  внутри запроса, в базу не попадает).
- `GET /healthz`, `/metrics`.

Не ищет сам (контекст из `retrieval`), не хранит документы. Владеет базой
`vektor_answer`: диалоги, реплики, цитаты, записи идемпотентности.

## Инварианты

- История диалога приходит только из базы: клиент передаёт `conversation_id`,
  а не транскрипт. Подсунуть модели чужой контекст через тело запроса нельзя.
- Повтор с тем же `client_message_id` возвращает сохранённый ответ; тот же ключ
  с другим текстом — `409 IDEMPOTENCY_CONFLICT`.
- В диалоге одна активная генерация: параллельный запрос получает
  `409 TURN_IN_PROGRESS` (частичный уникальный индекс `uq_turns_active`).
- Чужой `conversation_id` неотличим от несуществующего — `404`.
- `page_context` — недоверенный ввод: поля обрезаются, адрес принимается только
  `http(s)` без query и fragment, права от контекста не зависят. Он попадает в
  поисковый запрос и промпт как данные.
- `content_key` — только подсказка: документ по нему ищет сервер через
  `/internal/page-bindings` в `documents`. Найденная привязка повышает фрагменты
  документа в выдаче (`focus_document_ref`), но не ограничивает поиск. Нет
  привязки или `documents` недоступен — вопрос обрабатывается без неё.
- Брошенную генерацию при старте помечает `interrupted`, иначе диалог остался бы
  занятым навсегда.

## Архитектура

```
app/main.py        — HTTP-слой: маршруты, middleware, метрики, конверт ошибок
app/deps.py        — аутентификация и сборка сценариев над адаптерами
app/db.py           — пул, миграции и SQL диалогов
app/usecases/      — сценарии: AskQuestion, AskAboutFile, общий шаг генерации
app/ports.py       — что сценариям нужно от внешнего мира
app/errors.py      — AppError с кодами и текстами ошибок
app/settings.py    — значения из окружения (TOP_K, MAX_UPLOAD)
app/rag.py         — чистое ядро: промпт, парсинг ответа, цитаты, нарезка файла
app/guard.py       — чистый классификатор: инъекция в промпт, платёжные данные
app/clients.py     — клиенты зависимостей (retrieval, embedding, documents, LLM, JWKS)
```

Ядро (`rag`, `guard`) и сценарии не делают ввода-вывода напрямую: всё внешнее
приходит через порты. `main.py` только разбирает запрос и переводит `AppError` в
ответ; порядок «guard → поиск → LLM» живёт в сценариях и не повторяется в
маршрутах.

## Контракт

Запрос: `{"question", "conversation_id"?, "client_message_id"?, "page_context"?}`.
Пустой `conversation_id` — сервер создаст диалог. `page_context` сохраняется в
`turns.page_context` вместе с разрешённой привязкой, выделенный текст добавляется к
поисковому запросу, заголовок страницы — к промпту.

Ответ: `{"status": "ok"|"no_evidence", "answer", "citations": [...],
"conversation_id", "turn_id", "request_id"}`.

Цитаты зажимаются по выданному набору: модель не может сослаться на фрагмент вне
выдачи, дубликаты отбрасываются, порядок сохраняется.

## Порядок обработки

1. Проверка JWT (JWKS `auth`) — зависимость `authenticated`. Плохой токен → `401`,
   недоступность JWKS → `503` `AUTH_UNAVAILABLE`: отказ зависимости не
   маскируется под «нет авторизации».
2. Проверка `scp` (`403`): пустой набор доступов — некому искать.
3. Классификатор `guard`: инъекция в промпт или явная попытка передать платёжные
   данные → `403` с меткой причины. Правила только запрещают, ничего не пропускают.
4. Поиск через `retrieval` → при пустой выдаче `no_evidence` без вызова LLM.
5. Генерация в LLM (JSON `{"answer", "citations"}`), парсинг с fallback на текст.
6. Запись реплики: `completed`, текст ответа, цитаты и запись идемпотентности —
   одной транзакцией. Сбой любого шага переводит реплику в `failed`, и повтор с
   тем же ключом переиспользует её, а не создаёт вторую.

## Нарезка файла

`slices` режет текст по абзацам на окна до 1000 символов; абзац длиннее окна
режется на части, хвост не теряется. Векторные векторы ранжируют окна по близости
к запросу (`rank`), при деградации embedding — возвращаются первые `TOP_K`.

## Наблюдаемость

Middleware метрик использует шаблон маршрута как label — кардинальность
ограничена, 404 по мусорным путям складываются в `__unmatched__`. Счётчик
`answer_total` по статусам (`ok`, `no_evidence`).

## Отказы

| Код                      | Причина                               |
| ------------------------ | ------------------------------------- |
| `401 UNAUTHORIZED`       | Нет или неверный токен                |
| `403 FORBIDDEN`          | Нет прав, либо сработал классификатор |
| `404 CONVERSATION_NOT_FOUND` | Диалога нет или он чужой          |
| `409 TURN_IN_PROGRESS`   | В диалоге уже идёт генерация          |
| `409 IDEMPOTENCY_CONFLICT` | Ключ реплики занят другим вопросом  |
| `413 PAYLOAD_TOO_LARGE`  | Файл больше лимита                    |
| `503 SEARCH_UNAVAILABLE` | `retrieval` недоступен                |
| `503 AUTH_UNAVAILABLE`   | JWKS недоступен                       |
| `503 LLM_UNAVAILABLE`    | LLM не настроен или недоступен        |
| `502 LLM_BAD_OUTPUT`     | Модель вернула пустой ответ           |

## Тесты

`python -m pytest apps/backend/answer/tests` — парсинг ответа, цитаты, нарезка
файла, ранжирование, классификатор, идемпотентность и отказы хранилища. В CI
гоняется отдельной пачкой. SQL проверяется на стенде: миграции накатываются при
старте, инварианты — `infra/scripts/schema/answer-invariants.sql`.
