# Фронтенд AKS: два независимых пакета

В `frontend/` лежат два пакета, которые собираются раздельно и не делят ни
исходников, ни сборку:

```text
frontend/
  package.json          # npm workspaces: только оркестрация скриптов
  demo/                 # сайт-хост: лендинг «ВЕКТОР» + внедрение виджета
  widget/               # наш виджет: загрузчик, iframe-документ, весь общий код
```

## Почему так

Требование — чтобы виджет и демо собирались независимо (у каждого свой
`package.json` и свой `vite build`), но исходники виджета не дублировались, а
демо подключало виджет **только загрузчиком**, как любой внешний сайт.

Из двух вариантов выбран **monorepo на npm workspaces с internal-зависимостью**:

- `frontend/demo/package.json` объявляет `"@aks/widget": "*"`. npm поднимает в
  корне монорепозитория один `node_modules` и кладёт туда симлинк
  `node_modules/@aks/widget -> ../widget`.
- Демо **не импортирует ни одного исходника виджета**. Оно берёт только
  собранный артефакт `dist` виджета и отдаёт его наружу как обычную статику из
  `/aks/` — ровно так же, как его отдавал бы внешний CDN. Плагин в
  `demo/vite.config.ts` копирует (build) или отдаёт по запросу (dev) файлы из
  `node_modules/@aks/widget/dist`; при отсутствии сборки падает с понятной
  командой, а не молча.
- `demo/index.html` подключает виджет ровно как внешний сайт:
  `<script src="/aks-widget.js" async>` плюс `window.AKS_WIDGET` с `src`,
  `apiUrl` и `kbId`. Сам загрузчик — симлинк на `../../widget/aks-widget.js`,
  так что исходник загрузчика тоже не копируется.

Почему не «dev подключает `../widget/aks-widget.js` по относительному пути»:
путь в `node_modules` выражает настоящую зависимость (npm не даст собрать демо
без виджета), не привязывает демо к расположению виджета на диске и одинаково
работает в dev, в production-сборке и в `vite preview`.

Почему не «демо импортирует исходники виджета»: это связало бы сборки между
собой (демо нельзя было бы поставить на внешний сайт как чужой пример) и,
главное, скопировало бы весь виджет в бандл лендинга вместо одного iframe.

## Команды

Установка (один раз, из `frontend/` — поднимает оба пакета):

```bash
cd frontend
npm install
```

Сборка — виджет идёт первым, потому что демо включает его артефакт:

```bash
cd frontend
npm run build              # виджет, затем демо
npm run typecheck          # tsc -b --noEmit в обоих пакетах
npm run lint               # oxlint в обоих пакетах
```

По пакетам — каждая команда работает из своего каталога:

```bash
cd frontend/widget && npm install && npm run build
cd frontend/demo   && npm install && npm run build
```

Запуск для разработки (два терминала):

```bash
cd frontend/widget && npm run dev    # http://localhost:5175/widget.html — виджет отдельно
cd frontend/demo   && npm run dev    # http://localhost:5174 — лендинг с виджетом
```

Порядок такой: демо поднимается вторым, потому что плагин требует уже
собранный `widget/dist`.

## Как это устроено

- **Виджет** собирается с `base: "./"` и относительными ссылками на ассеты,
  поэтому его `dist` (`widget.html`, `widget.js`, `assets/`, `aks-widget.js`)
  можно положить под любой префикс — как на хосте, так и на CDN. Загрузчик
  копируется в корень `dist` плагином `emit-loader`, и весь `dist` становится
  самодостаточным бандлом для отдачи наружу.
- **Демо** получает этот `dist` через `@aks/widget` и монтирует под `/aks/`.
  В собранном демо это обычная статика рядом с лендингом, поэтому
  `npm run preview` в демо показывает работающий виджет.
- **Общение виджета с API** идёт только через `apiUrl` из `window.AKS_WIDGET`;
  токен не кладётся ни в `localStorage`, ни в URL, чаты живут в IndexedDB
  через dexie. Ничего из этого демо не меняет — оно и не должно.
- **Картинки** `demo/public/img/*.png` и `favicon.svg` — только для лендинга;
  в виджете статики нет.
- Фикс `dexie` + `EntityTable` живёт в `widget/tsconfig.app.json`: при
  `moduleResolution: "bundler"` dexie резолвится на свой `import-wrapper.d.mts`
  и теряет именованные типы, поэтому указан явный путь к `dexie.d.ts`. Путь
  задан двумя кандидатами, чтобы работать и в workspaces (`node_modules` в
  корне `frontend/`), и при одиночной установке в пакете.
