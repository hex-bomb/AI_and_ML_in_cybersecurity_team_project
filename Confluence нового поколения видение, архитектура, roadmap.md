# Confluence нового поколения: видение, архитектура, roadmap

Oct 10, 2026 · @Xavier

## 1. Видение и принципы

**Строим систему знаний, в которую можно скинуть любой корпоративный контент (Slack, почта, вики, заметки, тикеты, файлы) и сразу искать по нему с учётом прав доступа, актуальности и связей между документами.** Это «Confluence + Glean + личный second brain» в одном продукте с одним ядром.

Главная фишка и критерий любого решения: **универсальность приёма данных**. Новый источник добавляется написанием коннектора и маппинга, а не изменением ядра, схемы или поиска.

**Шесть принципов, которые защищают от переписывания:**

1. **Источник правды один: сырой слой (lake) + события.** Всё остальное (поисковый индекс, граф, PageRank, эмбеддинги) — производные представления, которые можно пересобрать из lake за часы.
2. **Единый конверт документа (envelope).** Любой объект приводится к одной схеме: id, источник, тип, владелец, ACL, время создания и правки, теги, текст, ссылки. Всё специфичное лежит в `extra` (JSON).
3. **ACL едет вместе с документом на каждом шаге**, включая индекс и MCP. Права, добавленные «потом», — главная причина провалов корпоративного RAG.
4. **Поиск сначала простой и измеримый.** Гибрид BM25 + вектор в одном Elasticsearch, замеры на собственном наборе вопросов, и только потом экзотика.
5. **Модульный монолит на Go, а не 15 микросервисов.** Kafka нужна для ингеста и пересчётов, остальное в одном деплое с чёткими границами пакетов.
6. **Каждая «умная» функция (граф, конфликты, PageRank) включается за флагом и добавляется как новый потребитель событий**, без изменений схемы хранения.

**Чего не делаем в первых версиях:** полноценный WYSIWYG-редактор как у Confluence (документы можно писать в Markdown), собственные модели эмбеддингов, мультирегиональность, real-time совместное редактирование.

**Для кого:** команда 50–5000 человек с разрозненными источниками знаний; отдельный сценарий для одиночки — личная база через desktop-приложение.

## 2. Уроки чужих проектов и исследований

**Главный вывод: на реалистичных корпоративных данных обычный BM25 даёт 68,8% правильных ответов, чистый векторный поиск — только 51,4%.** Поэтому база нашего поиска — Elasticsearch с сильной лексической частью, а эмбеддинги, граф и Hopfield — улучшения, которые нужно доказывать замерами.

| Источник | Что показал | Что берём в проект |
| --- | --- | --- |
| [EnterpriseRAG-Bench](https://github.com/onyx-dot-app/EnterpriseRAG-Bench), [статья arXiv 2605.05253](https://arxiv.org/abs/2605.05253) (Onyx + UC Berkeley) | \~500 000 синтетических документов из 9 источников (Slack \~275 тыс., Gmail \~120 тыс., Linear, Drive, HubSpot и др.), 500 вопросов в 10 категориях. BM25 / вектор (text-embedding-3-large + Qdrant) / агент с bash: correctness 68,8% / 51,4% / 60,6%; recall 68,4% / 46,0% / 55,8%. На вопросах «противоречивая информация» BM25 — 90%, вектор — 60%. «Полнота» (найти все релевантные) — самая сложная: \~35–40% у всех. | Берём как eval-набор для нашего поиска и как готовый набор данных для нагрузки lake. Точность извлечения сущностей 60–85%; граф «уходит» на 15–20% от истины за квартал без автообновления. | Hopfield: [Ramsauer et al., «Hopfield Networks is All You Need»](https://arxiv.org/pdf/2008.02217); [k-Hopfield, NeurIPS-W 2023](https://mlanthology.org/neuripsw/2023/davydov2023neuripsw-retrieving) | Современная сеть Хопфилда — это дифференцируемый слой внимания; k-Hopfield возвращает k ближайших «воспоминаний» и на малых ViT даёт сопоставимое качество с меньшим числом параметров. Доказательств преимущества над HNSW в поиске по миллионам документов я не нашёл. | Подробная критика — в разделе 5. В MVP не берём. |

Ограничения данных: EnterpriseRAG-Bench синтетический, оценка делалась LLM-судьёй (GPT-5.4), вопросы про метаданные (100 шт.) в основной замер не вошли. Цифры — ориентир, не гарантия.

**Ошибки, которые не повторяем:**

1. **Векторный поиск как единственный.** Кодовые имена проектов и жаргон модель эмбеддингов не знает: лексическая часть обязательна.
2. **Post-filter прав доступа.** Разрешённый чанк уже в памяти, контексте LLM и логах. Фильтруем в самом запросе к индексу.
3. **Тихие потери в коннекторах.** Нужны метрики «отставание от источника» и периодическая сверка количества документов.
4. **Граф на всём корпусе через LLM.** Дорого, неточно, быстро устаревает.
5. **Нет eval-набора.** Без него нельзя отличить улучшение от регрессии; ориентир вендора: более 70% context relevance и 80% faithfulness перед релизом.
6. **Агентные циклы по умолчанию.** bash-агент лучше всех по полноте, но до 10 минут на вопрос, а агентные циклы вообще тратят в 3–10 раз больше токенов. Не в MVP; позже как режим «глубокий поиск».

## 3. Общая архитектура

**Один Go-бинарник в двух режимах (api и worker), данные сначала попадают в lake, а всё остальное — поисковый индекс, граф, PageRank — строится из него воркерами.**

&#91;embedded content: архитектура · 4 клиента, монолит на Go, Kafka, 4 хранилища\]

Читать схему сверху вниз: клиенты входят через внешний сервер авторизации (раздел 6, на схеме он не показан), Go-код только проверяет токен. Путь записи — правая колонка: Ingest API → Kafka → Workers → хранилища. Путь чтения — левая: API и MCP читают Elasticsearch и PostgreSQL напрямую, без Kafka. Выделенные цветом ClickHouse и S3 — и есть lake: стратегия восстановления — пересобрать всё остальное из них.

**Два решения, зависящие от вас:**

- **Многоарендность.** Если продукт для одной компании — `tenant_id` всё равно закладываем с первого дня: это дешёво сейчас и очень дорого добавлять потом.
- **Развёртывание.** SaaS в вашем облаке или self-hosted у клиента. Для второго только Docker Compose и Helm-чарт; полные возможности для air-gapped установок (локальные модели эмбеддингов) закладываем через интерфейс `Embedder` уже сейчас. Onyx поставляет именно такие варианты, и это заметный канал продаж ([Onyx](https://onyx.app/insights/self-hosted-rag)).

## 4. Модель данных и ингест

**Универсальность держится на трёх вещах: один конверт документа, одна публичная «push-дверь» для любых данных и конвейер из пяти стадий поверх Kafka.** Коннекторы Slack/почты — просто клиенты этой двери, поэтому новый источник не трогает ядро.

**Где что хранится.**

| Хранилище | Роль | Почему именно оно |
| --- | --- | --- |
| Object storage (S3/MinIO) | Сырые файлы и вложения, content-addressed (ключ = хэш) | В вашем стеке его нет, но без него PDF/картинки нельзя хранить дёшево. **Добавляем в стек.** |
| ClickHouse | Append-only журнал событий lake (`raw_events`), версии текста, поисковые логи, клики, оценки, метрики ингеста | Колоночный, дешёвый на объёмах, шардируется штатно (Distributed). Не пишем своё шардирование. |
| PostgreSQL | Пользователи, группы, ACL, настройки источников и курсоры коннекторов, реестр документов (текущая версия), комментарии, рёбра графа | Транзакции и связи: то, что должно быть консистентным. |
| Elasticsearch | Производный поисковый индекс (BM25 + векторы + ACL-поля) | Всегда перестраиваемый из lake: не источник правды. |
| Kafka | Шина событий между стадиями и потребителями | Партиции по хэшу `tenant_id + doc_id` — это и есть ваше «шардирование» на старте. |

**Конверт документа (единственная схема для всего).**

| Поле | Что хранит |
| --- | --- |
| `doc_id` | Стабильный идентификатор: хэш `tenant + source + external_id` |
| `tenant_id`, `source`, `kind` | Организация, источник (slack, gmail, note, ...), тип (message, thread, page, file, ticket) |
| `title`, `body` | Нормализованный текст (Markdown) |
| `url`, `parent_id`, `links[]` | Ссылка на оригинал, контейнер (канал, папка, тред), исходящие ссылки (основа для PageRank и графа) |
| `owner`, `author` | Владелец (для уведомлений) и автор |
| `created_at`, `updated_at`, `ingested_at` | Три разные даты: свежесть считаем по `updated_at` источника, лаг — по `ingested_at` |
| `acl` | Список принципалов (группы ресурсов, раздел 6) |
| `tags[]` | Теги: ручные и автоматические |
| `content_hash`, `version` | Для идемпотентности и дедупликации |
| `extra` | Любые специфичные поля источника (JSON): эмодзи-реакции Slack, статус тикета и т.п. |

**Конвейер ингеста.**

1. **Collect.** Коннектор или `POST /api/v1/ingest` кладут сырьё в S3 и событие в топик `raw`.
2. **Normalize.** Парсер по MIME-типу (md, html, pdf, docx, txt, аудио → транскрипт) строит конверт → топик `normalized`.
3. **Enrich.** Дедупликация по `content_hash`, чанкинг по заголовкам (Slack — по тредам, не по одиночным сообщениям), префикс «название + путь» к каждому чанку, эмбеддинги, извлечение ссылок.
4. **Index.** Upsert в Elasticsearch вместе с ACL; удаление — через событие-надгробие (tombstone).
5. **Derive.** Независимые потребители того же потока: PageRank, граф, конфликты, уведомления. Они не блокируют получение документа в поиске.

Правила надёжности: все стадии идемпотентны (ключ `doc_id + content_hash`), у каждого топика есть dead-letter-очередь, схемы событий версионируются (`raw.v1`), а любой индекс можно удалить и воссоздать из lake без обращения к источникам.

**Контракт коннектора на Go** (пусть будет один интерфейс, даже если вначале коннекторы живут внутри монолита):

```go
type Connector interface {
    Name() string
    // возвращает порцию и новый курсор; пустой курсор = полный обход
    Pull(ctx context.Context, cursor string) (items []RawItem, next string, err error)
    // кто может читать этот объект в источнике (внешние группы)
    Permissions(ctx context.Context, item RawItem) ([]Principal, error)
}
```

Шардирование в MVP — один шард везде, но с расчётом на рост: `tenant_id` в каждой строке и ключе партиции, индексы Elasticsearch на базе alias, ClickHouse — через таблицы, которые легко превратить в Distributed.

## 5. Поиск и ранжирование

**Ядро поиска: два запроса в Elasticsearch (BM25 и kNN по HNSW), слияние через RRF в Go-коде и ограниченные бусты от PageRank, свежести и оценок.** HNSW уже встроен в Elasticsearch (поле `dense_vector`), отдельная векторная БД не нужна. Hopfield в ядро не берём, а проверяем как эксперимент на eval-наборе.

**Путь запроса:**

1. Из токена берём пользователя и разворачиваем его в список принципалов (группы, роли).
2. В Elasticsearch уходят два запроса с одним и тем же фильтром `tenant_id` + `acl ∈ принципалы`: лексический (анализатор `russian` для морфологии плюс отдельное поле без стемминга для кодовых имён и идентификаторов) и kNN (фильтр передаётся внутрь `knn.filter`).
3. Результаты сливаем **RRF в Go-коде** (около десяти строк). Так мы не зависим от того, в какой лицензионный тариф Elastic относит встроенный RRF-retriever: на страницах документации, которые я открыл, это не указано, проверьте для своей версии.
4. Бусты (ниже), затем опциональный cross-encoder rerank топ-50 за флагом.
5. В ответе возвращаем объяснение: почему документ наверху (BM25, вектор, свежесть, авторитет). Это снижает недоверие к выдаче.

**Критика Hopfield (мой анализ на основе формулировки из [статьи Ramsauer et al.](https://arxiv.org/pdf/2008.02217), не готовый результат из литературы).**

- Шаг обновления современной сети Хопфилда — это один softmax-слой внимания по всем сохранённым векторам. Для поиска это то же самое, что плотный поиск по N векторам; на миллионах чанков вам всё равно нужен ANN, то есть HNSW. «HNSW + Hopfield» не два слоя, а два названия одного шага.
- Если применить обновление к топ-k от HNSW, получится softmax-взвешенное среднее найденных векторов, то есть новый запрос. Это по смыслу pseudo-relevance feedback (как Rocchio). Выход — вектор, а не документ, ранжировать всё равно придётся по сходству.
- Заявленная ёмкость ассоциативной памяти важна, когда память — единственное хранилище. У нас есть полная копия данных в lake, поэтому это преимущество не работает.
- [k-Hopfield (NeurIPS-W 2023)](https://mlanthology.org/neuripsw/2023/davydov2023neuripsw-retrieving) показывает пользу на малых ViT; доказательств выигрыша на корпоративном поиске я не нашёл.
- Слабое звено поиска по бенчмарку — именно векторная часть (51,4% против 68,8% у BM25), и на неё влияют модель эмбеддингов и жаргон, а не способ обновления запроса.

**Решение:** в MVP реализуем интерфейс `QueryExpander` с пустой реализацией. В фазе 3 добавляем Hopfield-расширение запроса как плагин и оставляем его, только если он поднимает nDCG@10 на вашем наборе вопросов.

**Эмбеддинги.** Нужна мультиязычная модель с хорошим русским (кандидаты: bge-m3, multilingual-e5; выбирать по вашему eval, а не по таблицам лидеров). Модель за интерфейсом `Embedder`, версия модели хранится в документе, переиндексация идёт новым полем `vec_v2` и переключением alias.

**Сигналы ранжирования (пункт 6):**

| Сигнал | Как считаем | Где живёт |
| --- | --- | --- |
| Авторитет (PageRank) | Граф из явных ссылок между документами, упоминаний, Slack-пермалинков и (позже) co-search рёбер из кликов. Считается пакетно раз в сутки на тенант | Поле `authority` в ES, частичное обновление |
| Свежесть | Экспоненциальное затухание от `updated_at` с периодом полураспада по типу: сообщение Slack — недели, регламент — год. Кнопка «подтвердить актуальность» у владельца сбрасывает возраст (`reviewed_at`) | Функция в запросе ES, `reviewed_at` в документе |
| Оценки like/dislike | Событие с причиной (устарело, неверно, дубль, мало контекста, нет доступа) пишется в ClickHouse; агрегат со сглаживанием (нижняя граница Вильсона), чтобы один дизлайк не топил документ | Поле `quality` в ES, события в ClickHouse |

Итоговая формула; каждый множитель ограничен диапазоном 0,5–1,5, чтобы сигналы не перебивали релевантность:

```latex
s(d) = s_{RRF}(d) \cdot (1 + w_a \, a_d) \cdot (1 + w_q \, q_d) \cdot f_{type}(t_d)
```

Веса подбираем на eval-наборе. Когда накопятся клики, заменяем ручную формулу на обученное ранжирование (learning to rank) без смены остальной архитектуры.

**Риск PageRank:** скаляр, посчитанный по закрытым документам, слегка раскрывает факт ссылок на них. На MVP принимаем; для строгих тенантов считаем граф только по документам, видимым всем.

**Метрики качества поиска:** nDCG@10, Recall@50, MRR на eval-наборе; для ответов — faithfulness и context precision (RAGAS или DeepEval). Любое изменение ранжирования проходит через этот набор до выката.

## 6. Доступ и аутентификация

**Права проверяются в самом запросе к индексу по схеме AGDLP, а вход делегируется готовому провайдеру (SSO через OIDC/SAML), собственную систему паролей не пишем.**

### AGDLP в нашей модели

| Шаг AGDLP | У нас | Пример |
| --- | --- | --- |
| Account | Пользователь | `anna@corp.ru` |
| Global group | Группа людей по роли или команде, приходит из IdP (claim `groups` или SCIM) | `team-backend`, `hr-all` |
| Domain Local group | Ресурсная группа: «кто может читать эту коллекцию» | `res:space-platform:read` |
| Permission | Право ресурсной группы на контейнер (space, канал, папка) | read / write / admin |

Правила: пользователи входят только в глобальные группы, глобальные группы входят в ресурсные, права назначаются только ресурсным группам. Запретов (deny) нет: только разрешения, иначе фильтр в индексе усложняется. Права личных заметок: `acl = [user:<id>]` и больше никто.

### Как это попадает в индекс

Права висят на **контейнере** (`space_id`: канал Slack, папка, ящик), а точечный `acl[]` на документе нужен только для исключений. Фильтр в каждом запросе:

```json
{ "bool": { "filter": [
  { "term":  { "tenant_id": "t1" } },
  { "bool": { "should": [
      { "terms": { "space_id": ["<доступные пользователю space>"] } },
      { "terms": { "acl":      ["<principals пользователя>"] } }
  ], "minimum_should_match": 1 } }
] } }
```

Почему так:

- Изменение прав на space применяется мгновенно и **не требует переиндексации** документов, только пересчёта списка доступных space у пользователя (кэш на минуту-две, сбрасывается событием `acl.changed` из Kafka). Вендорный разбор называет это главным риском: права должны доходить до индекса за минуты, а не после ночной пересборки ([Atolio](https://www.atolio.com/blog/enterprise-rag-guide)).
- Нативный document-level security Elasticsearch нам не подходит: наши пользователи не пользователи ES, а в [документации ограничений DLS](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/security-limitations.html) указано, что `terms`-lookup в ролевых запросах не поддерживается, статистика релевантности считается без учёта фильтра роли, а агрегации могут раскрывать термины из недоступных документов. Поэтому фильтр строит наш Go-код, а агрегации по чужим данным отдаём только после того же фильтра.
- Защита в глубину: перед тем как отдать top-N в UI или в контекст LLM через MCP, повторно проверяем `can_read(user, doc_ids)` по Postgres. Это дёшево для 20–50 документов и закрывает окно устаревшего индекса.
- Размер списка: по умолчанию Elasticsearch ограничивает `terms` числом 65 536 значений (`index.max_terms_count`, из памяти, проверьте для своей версии). Для 5000 человек этого хватает с запасом.
- Права из внешних систем (каналы Slack, шеры Drive) коннектор превращает в ресурсные группы через `Permissions()` (раздел 4), пользователи сопоставляются по email.

### Аутентификация

**Решение: между приложением и корпоративным IdP ставим один готовый сервер авторизации (Keycloak или Zitadel, выбрать по тому, что умеет ваша команда эксплуатировать). Go-бэкенд только валидирует JWT.**

- SSO: корпоративные IdP (Entra ID, Okta, Google Workspace, Keycloak) подключаются к серверу авторизации по OIDC или SAML. Для маленьких команд без IdP тот же сервер хранит логин-пароль и 2FA.
- Группы: на MVP берём из claim `groups` при входе, пользователя создаём при первом входе (JIT). Во второй фазе добавляем SCIM, чтобы увольнение отзывало доступ за минуты, а не при следующем входе.
- Токены не содержат список групп (он устаревает и раздувает токен): принципалы разворачиваются на сервере по `sub` из кэша.
- Ингест-API: сервисные токены с областью `ingest:write` на конкретный источник, хэш хранится в Postgres.

| Клиент | Поток | Примечание |
| --- | --- | --- |
| Web | Authorization Code + PKCE, серверная сессия (httpOnly cookie) | Go выступает BFF, токены в браузере не светятся |
| Desktop | Authorization Code + PKCE через системный браузер и loopback-redirect | Refresh-токен в системном хранилище ключей (Keychain, Credential Manager) |
| MCP | OAuth 2.1 по [спецификации MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) | Ниже |
| Ингест / скрипты | Сервисный токен | Без прав на чтение |

### MCP-авторизация

По [спецификации MCP от 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) наш MCP-сервер — это OAuth 2.1 resource server. Обязательное:

1. Публиковать Protected Resource Metadata (RFC 9728), по нему клиент находит сервер авторизации.
2. Отвечать `401` с `WWW-Authenticate` и `resource_metadata`; при нехватке прав — `403 insufficient_scope`.
3. Принимать только токены, выпущенные для нашего ресурса (audience по RFC 8707 `resource`), и не принимать и не пересылать чужие токены.
4. Клиент использует PKCE и параметр `resource` в обоих запросах; регистрация клиента — через Client ID Metadata Documents, а Dynamic Client Registration в спецификации помечена как устаревшая.

Проверьте выбранный сервер авторизации на поддержку именно этих пунктов до выбора. MCP-инструмент всегда действует **от имени пользователя** с тем же фильтром прав, никакого суперпользовательского сервисного аккаунта.

## 7. Продуктовые функции (пункты 4–10)

**Каждая функция — это отдельный потребитель событий или тонкий клиент к одному и тому же API; ядро (lake + индекс + ACL) они не меняют.**

### Web и MCP (п. 4)

- Web: React + Vite + Effector + TanStack (Query для данных, Router для страниц). Экраны MVP: поиск с фильтрами и объяснением ранжирования, просмотр документа, оценка like/dislike с причиной, администрирование источников и групп.
- MCP-сервер живёт в том же Go-бинарнике (Streamable HTTP). Инструменты: `search`, `get_document`, `related`, `create_note`, `report_issue`. В ответе поиска возвращаем не только текст, но и `url`, `updated_at`, `authority`, `has_open_comments`, чтобы агент сам мог взвесить источник.
- Риск: документы в lake могут содержать чужие инструкции (любое сообщение в Slack). Результаты MCP помечаем как данные, ограничиваем размер, а записывающие инструменты (`create_note`, `report_issue`) требуют явного подтверждения пользователя в клиенте.

### Desktop-приложение (п. 5)

- Тонкая оболочка над тем же web-UI: **Wails** (Go + web-фронт, ближе всего к вашему стеку) или Tauri. Выбор подтвердить прототипом глобального хоткея на Windows, macOS и Linux — это самое хрупкое место обеих.
- Окно быстрой заметки по хоткею: текст, файл или диктовка. Заметка уходит в `POST /api/v1/ingest` с `kind=note`, `acl=[user:<id>]`.
- Если сети нет, заметка сохраняется в локальную очередь (SQLite) и отправляется позже. Идемпотентность по `doc_id` защищает от дублей.
- Диктовка: в MVP не делаем, в фазе 2 добавляем серверный STT (whisper-совместимый сервис) за интерфейсом `Transcriber`.

### Комментарии и уведомления (п. 7)

- Комментарий хранится в Postgres: документ, версия, цитата-якорь (текст + смещение), автор, статус (открыт, исправлено, отклонено), тип (вопрос, устарело, ошибка).
- Для внешних документов (Slack, Drive) мы **не пишем обратно в источник**: комментарии живут как наложение в нашей системе, владелец берётся из `owner` конверта.
- Событие `comment.created` уходит в Kafka, потребитель `notifier` шлёт письмо, сообщение в Slack или уведомление в UI владельцу. Тип «устарело» и «ошибка» дополнительно идёт в сигнал `quality` и в очередь конфликтов.
- Открытые комментарии индексируются как аннотации документа и показываются рядом с ним в выдаче и в MCP. Пример из вашей задачи: «ручка уже api/v2» увидит и человек, и агент до того, как владелец поправит текст.

### Версии документов (п. 8)

**Не берём настоящий Git как хранилище.** Git плохо подходит для сотен тысяч мелких объектов (сообщения Slack) и для конкурентной записи из веба.

- Для ингестированных документов версионирование бесплатно: каждое изменение — новое событие в `raw_events` с новым `content_hash`, историю можно показать из ClickHouse.
- Для документов, написанных в самой системе, версия = неизменяемый снимок (S3, ключ по хэшу) + запись в Postgres: `doc_id`, `version`, `parent_version`, `author`, `message`, `hash`. Дифф считаем на лету.
- Совместимость с Git остаётся как опция фазы 4: односторонняя выгрузка space в Git-репозиторий (удобно для бэкапа и ревью через pull request) без обратной синхронизации.

### Конфликты знаний (п. 9)

Что говорят исследования: [LLM как «валидатор контекста»](https://arxiv.org/abs/2504.00180) на синтетических данных лучше всего дали 0,71 accuracy (Claude-3 Sonnet с CoT), при высокой точности и низкой полноте, то есть редко ошибаются в положительную сторону, но пропускают много настоящих противоречий. [ConflictRAG](https://arxiv.org/abs/2605.17301) сообщает о 88,7% F1 при двухступенчатой схеме: дешёвый классификатор на эмбеддингах отбирает пары, LLM решает только сомнительные; по оценке авторов это дешевле примерно на 62% против «LLM на всё». Оба результата получены на синтетических или самосозданных наборах и на моделях, которые давно сменились: считайте это ориентиром, а не гарантией.

Наш дизайн:

1. **Генерация кандидатов** (дёшево): пары документов с высокой близостью эмбеддингов, общими сущностями (версии API, названия систем) и разными датами правки.
2. **Проверка** LLM только для кандидатов, асинхронно, на стадии Derive.
3. **Тип конфликта**: фактический, временной, мнение. Временной решается свежестью, остальные — только пометкой.
4. **Человек решает.** Система создаёт «возможный конфликт» с цитатами обоих документов и уведомляет владельцев, ничего не переписывает.
5. В MVP — только для написанных в системе документов и вики, не для Slack: там шума слишком много.

### Выборочные графы (п. 10)

Граф строим только из дешёвых и надёжных связей, **без LLM-извлечения сущностей по всему корпусу** (по причинам из раздела 2).

| Тип ребра | Откуда берётся | Вес |
| --- | --- | --- |
| `explicit` | Админ или владелец связал документы вручную | Высокий, не затухает |
| `link` | Гиперссылка, упоминание, permalink внутри текста | Средний |
| `co_search` | Документы, которые открывают в одной поисковой сессии (из ClickHouse) | Затухает со временем, пересчёт раз в сутки |
| `thread` | Один тред, один тикет, одно письмо | Средний |

Хранение: таблица `doc_edges(src, dst, type, weight, created_by)` в Postgres. Использование: (а) блок «связанные документы» с расширением на один шаг от топ-результатов, строго внутри ACL-фильтра; (б) граф для PageRank; (в) кандидаты для проверки конфликтов. Отдельная графовая БД нужна, только если запросы будут глубже двух шагов — через 90 дней после запуска измеряем, окупается ли поддержка (так советует [практический разбор GraphRAG](https://tianpan.co/blog/2026-04-09-graphrag-production-when-vector-search-hits-ceiling)).

## 8. Как не уйти в overengineering

**Правило: новая технология появляется только тогда, когда метрика на eval-наборе или на нагрузке показала, что простого решения не хватает.** Остальное записано как «потом» и спрятано за интерфейсом, чтобы замена не требовала переписывания.

| Идея | Что делаем в MVP | Когда усложняем |
| --- | --- | --- |
| Hopfield поверх HNSW | Ничего. Интерфейс `QueryExpander` с пустой реализацией | Фаза 3, если поднимает nDCG@10 на вашем наборе |
| Графовая БД | Таблица `doc_edges` в Postgres | Если запросы глубже двух шагов и поддержка графа окупилась за 90 дней |
| Свой шардинг lake | Один шард, `tenant_id` в ключе партиции | Когда один кластер перестанет справляться с объёмом |
| 15 микросервисов | Один Go-бинарник, режимы `api` и `worker` | Когда команды начнут мешать друг другу в одном репозитории |
| Свой сервер логина | Готовый Keycloak или Zitadel | Не усложняем |
| Настоящий Git | Неизменяемые снимки + `raw_events` | Фаза 4: односторонний экспорт |
| Диктовка в desktop | Только текст и файл | Фаза 2–3 |
| 40 коннекторов | Три: заметки, файлы/Markdown, Slack | По запросу клиентов, по одному |
| LLM-граф по всему корпусу | Нет | Только для узких типов сущностей, если упрётся |
| Агентный глубокий поиск | Нет | Отдельный режим «искать глубоко», позже |

**Где ваш стек уже тяжёл.** Postgres, ClickHouse, Elasticsearch, Kafka и S3 — пять stateful-систем на старте, это самая большая цена всей затеи. Два способа её снизить, решение за вами:

- Оставить всё как задумано, если эти системы у вас уже эксплуатируются. Kafka в режиме KRaft на одном узле, один узел ClickHouse, один узел Elasticsearch.
- Если команда маленькая, на фазе 1 писать `raw_events` и логи в партиционированную таблицу Postgres за интерфейсом `EventStore`, а ClickHouse подключить на фазе 2, когда появятся клики и оценки. Моя рекомендация: так, и вы ничего не теряете, потому что lake всё равно пересобирается из S3.

**Четыре шва, на которых держится развитие без переписывания.** Для каждого один Go-интерфейс и версионируемая схема событий:

1. `Connector` (откуда данные),
2. `Embedder` (как считать векторы, версия модели в документе),
3. `Ranker` и `QueryExpander` (как ранжировать и расширять запрос),
4. `EventBus` и `EventStore` (Kafka и ClickHouse можно заменить, не трогая остальной код).

**Три правила процесса:**

- Любая «умная» функция включается флагом и отключается без потери данных.
- Любое изменение ранжирования проходит eval-набор до выката.
- Любая новая колонка в конверте добавляется только в `extra`, и в первоклассное поле переезжает после того, как её начали использовать минимум два потребителя.

### Критерии готовности MVP (мои предложения, подгоните под себя)

- **Права:** автотест в CI на каждый PR проверяет матрицу «пользователь × документ» и сообщает об ошибке при любой утечке.
- **Качество:** eval-набор не меньше 100 реальных вопросов; nDCG@10 гибрида не ниже BM25-базы; бусты включаются только после этого замера.
- **Свежесть данных:** у каждого коннектора есть метрика «последнее успешное обновление» и алерт на отставание.
- **Восстановление:** индекс хотя бы раз полностью пересобран из lake по учебной тревоге.
- **Удаление:** документ, удалённый в источнике, исчезает из выдачи (проверяется тестом).
- **Вход:** SSO через ваш IdP работает, отзыв доступа действует в пределах срока кэша прав.

### Что не меняется от фазы к фазе

Конверт документа, версия событий `v1`, модель AGDLP с фильтром в индексе и четыре интерфейса из раздела 8. Новое добавляется потребителями событий и флагами, а не изменением этих четырёх вещей.

## 10. Риски, открытые вопросы и источники

**Три риска бьют сильнее всего: утечка прав доступа, «тихое» отставание коннекторов и тяжёлая эксплуатация пяти хранилищ.**

| Риск | Как закрываем |
| --- | --- |
| Утечка прав через поиск, кэш, логи, MCP | Фильтр в запросе к индексу + повторная проверка по Postgres + автотест матрицы прав в CI. В логах запросов не храним текст документов. |
| Коннектор молча перестал обновляться | Метрика «возраст последнего обновления», алерт, периодическая сверка числа документов с источником. |
| Векторный поиск слаб на русском и внутреннем жаргоне | BM25 как база, выбор модели по eval на ваших данных, словарь синонимов и аббревиатур в Elasticsearch. |
| Пять stateful-систем | Раздел 8: замена ClickHouse на Postgres в начале, один узел везде, Docker Compose. |
| Встраивание чужих инструкций (prompt injection) из Slack и почты | Результаты MCP — данные, записывающие инструменты только с подтверждением пользователя. |
| Стоимость эмбеддингов и LLM | Кэш по `content_hash`, пакетные вызовы, LLM только на сомнительных парах (конфликты) и только в фазе 3. |
| Лицензия Elasticsearch | По [FAQ Elastic](https://www.elastic.co/pricing/faq/licensing) код доступен по SSPL 1.0, AGPLv3 и ELv2, стандартный дистрибутив — под ELv2. Если будете продавать SaaS или поставлять клиентам, покажите условия юристу; я не юрист. |
| Персональные данные в почте и мессенджерах | Сроки хранения и удаление по правилу tombstone с первого дня; требования по месту хранения (например, 152-ФЗ) обсудить с юристом. |

**Что я не проверил и что нужно проверить прототипом до старта:**

- В каком лицензионном тарифе Elastic находится встроенный RRF-retriever (на открытых мной страницах этого нет). Мы обходим вопрос, сливая результаты в Go.
- Предфильтр внутри `knn.filter` и поведение при большом списке совпадений на вашей версии Elasticsearch (по моим знаниям фильтр применяется во время поиска, страница документации, которую я открыл, этого не подтвердила).
- Предел `index.max_terms_count` для списка прав пользователя.
- Хоткей в Wails и Tauri на трёх ОС.
- Какой из Keycloak и Zitadel покрывает требования MCP-спецификации (Client ID Metadata Documents или DCR, ресурсные индикаторы).
- Утверждение об эквивалентности шага Hopfield и внимания — из моего знания статьи Ramsauer et al. (саму статью я нашёл поиском, но не открывал).
