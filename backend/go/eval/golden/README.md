# eval/golden — размеченный набор вопросов

Файл `golden.jsonl` — 141 вопрос с разметкой, по которому считаются
метрики качества поиска. Это тот набор, о котором §5 документа
«Confluence нового поколения» говорит: «Любое изменение ранжирования
проходит через этот набор до выката», и §9 превращает в ворота MVP:
«eval-набор не меньше 100 реальных вопросов; nDCG@10 гибрида не ниже
BM25-базы; бусты включаются только после этого замера».

Прогоняет набор `kbeval`:

```sh
cd backend/go
go run ./eval/cmd/kbeval -golden eval/golden/golden.jsonl -mode=compare \
    -backend=fixture -api /tmp/hits.json -out /tmp/report.json
```

## Формат

JSON Lines: один вопрос — одна строка. Строки, начинающиеся с `#` или
`//`, и пустые строки пропускаются. Разбор строгий: битая строка, дубль
`id`, нулевая оценка или вопрос без разметки останавливают прогон, а не
молча выкидываются.

Две настоящие строки файла:

```json
{"id":"gk-001","query":"Какой диаметр заготовки над шпинделем у токарно-фрезерного станка ВЕКТОР-16?","relevant":[{"doc_id":"vektor-cnc-16","grade":3}],"kind":"single_hop","tags":["cnc","specs"]}
{"id":"gk-002","query":"Какова наибольшая длина точения у станка ВЕКТОР-16?","relevant":[{"doc_id":"vektor-cnc-16","grade":3},{"doc_id":"vektor-equipment-care","grade":2}],"kind":"single_hop","tags":["cnc","specs"]}
```

| Поле | Обяз. | Значение |
| --- | --- | --- |
| `id` | да | Уникальный идентификатор вопроса. Дубликат — ошибка разбора. |
| `query` | да | Текст запроса, как его задал бы пользователь. |
| `relevant` | да | Массив `{doc_id, grade}`. Непустой, **кроме** вопросов-ловушек. |
| `kind` | да | Категория: `single_hop`, `multi_hop`, `temporal`, `contradiction`, `completeness`. |
| `tags` | нет | Доменные метки (`welding`, `pricing`, `cnc`, …). Считаются как группы, чтобы видеть просадку на одном участке знаний, замаскированную ростом на другом. |
| `expected_empty` | нет | `true` — вопрос-ловушка, правильный ответ «ничего не найдено». |

`grade` — graded relevance: `1` частично релевантен, `2` релевантен,
`3` эталонный ответ. Ноль запрещён: «нерелевантен» по набору не значит
«не должен находиться», иначе разметка раздулась бы до всех документов
корпуса.

`expected_empty: true` означает «здесь честно сказать „не знаю“». Для
таких вопросов считается **false-positive rate**: непустая выдача хуже
пустой, потому что агент получит уверенный неверный ответ вместо честного
отказа. Такие вопросы не входят в средние nDCG/Recall/MRR — у них нет
разметки, и нулевой nDCG от пустой выдачи был бы успехом, а не провалом.

## Как добавить вопрос

1. Дописать одну строку в `golden.jsonl` (можно в конец — порядок строк не
   влияет на метрики).
2. Проверить разметку: `go test ./eval/ -run TestShippedGoldenSet`.
3. Прогнать `kbeval` и убедиться, что число вопросов в сводке выросло и
   гейт по-прежнему считается.

Тесты `TestShippedGoldenSet*` в `runner_test.go` — единственная защита от
правки файла, который никто не перечитывает. Они проверяют: набор
читается, в нём ≥ 100 вопросов (§9), все `id` уникальны, у каждого
вопроса есть размеченный документ (кроме ловушек), категории и оценки в
допустимых значениях, есть все ключевые классы вопросов, а документы в
разметке существуют в корпусе фикстур. Последняя проверка особенно важна:
идентификатор документа, которого нет в корпусе, тихо обнуляет все
метрики по вопросу и выглядит как провал поиска.

## Огранинения (честно)

**Это синтетические вопросы, написанные по содержимому фикстур, а не 100
реальных вопросов пользователей.** §9 требует «не меньше 100 реальных
вопросов». Формально требование выполнено по количеству (141 > 100), но
не по природе: у набора нет истории запросов, нет формулировок, набранных
людьми вслепую, нет опечаток, нет вопросов на стыке двух документов,
которые человек не может назвать словами «сравни X и Y», и нет
распределения реального трафика — здесь его искусственно выровняли по
классам. Число 141 создаёт ложное ощущение готовности: набор проходит
формальную проверку §9, но измеряет способность искать по корпусу из
десяти документов, на котором любая стратегия ранжирования покажет
высокий результат.

Что из этого следует на практике:

- **Абсолютные цифры переносить нельзя.** nDCG@10 = 0.9 на этом наборе и
  nDCG@10 = 0.9 на реальной базе — разные вещи: здесь корпус настолько
  мал, что BM25 находит почти всё. Приемлемо только **относительное**
  сравнение «гибрид против BM25 на тех же вопросах» — ровно то, что делает
  гейт.
- **Нет оценок удовлетворённости.** Разметка проставлялась по совпадению
  темы с содержимым документа, а не человеком, который читал бы вопрос и
  документ вместе. Часть оценок grade=2 спорна: «частично релевантен»
  нигде не определена формально.
- **Нет английской части корпуса.** 6 вопросов помечены `en`, но в
  размеченных документах нет англоязычного текста, который дал бы этим
  вопросам предмет поиска.
- **Нет реального распределения сложности.** 73% набора — `single_hop`.
  В трафике такого соотношения не бывает, и гейт, проходящий на таком
  наборе, систематически недооценивает риск просадки на многошаговых
  вопросах.
- **Нет мультиязычности и опечаток.** Русская морфология в Elasticsearch
  настроена анализатором `russian`, но набор это не проверяет.

Что должно измениться до релиза:

1. **Заменить на реальные вопросы.** Минимум 100 штук из логов или
   телеметрии поиска за первый месяц эксплуатации, с распределением
   пропорционально реальному трафику, а не по классам. Текущий набор
   сохранить как регрессионный для офлайн-разработки, но перестать
   считать его выполнением §9.
2. **Провести двойную разметку.** Минимум два независимых разметчика на
   пересекающейся выборке, с измерением согласия (Cohen's kappa). Без
   этого «идеальная выдача даёт nDCG = 1.0» — таврология, а не
   подтверждение качества метрик.
3. **Откалибровать grade.** Определить формально, что значит grade=2,
   и проверить, что разметчики понимают это одинаково.
4. **Расширить корпус.** 11 документов — это не «корпоративная база
   знаний». Минимально нужны документы с разной длины (проверка
   нормализации по типу документа из §2), устаревшие версии (проверка
   веса свежести), документы с конфликтующими фактами (проверка
   `contradiction`) и неанглийские.
5. **Добавить измерение faithfulness и context precision** для ответов
   (раздел 5 упоминает RAGAS/DeepEval). Текущий набор измеряет только
   ранжирование, а не качество ответа.

## Внешний ориентир

В разделе 2 документа разобран [EnterpriseRAG-Bench](https://github.com/onyx-dot-app/EnterpriseRAG-Bench)
(Onyx + UC Berkeley, ~500 000 синтетических документов из 9 источников,
500 вопросов в 10 категориях): BM25 — 68,8% correctness, чистый векторный
поиск — 51,4%. Отсюда и решение §5: основа — лексическая часть, эмбеддинги,
граф и Hopfield — улучшения, которые надо **доказывать замерами**. Гейт
«гибрид не хуже BM25-базы» — это прямая проверка того, что добавленная
сложность не ухудшила то, что уже работает.

Собственный набор из этой папки к EnterpriseRAG-Bench неприменим напрямую:
у него другой корпус и другая разметка. Сравнимы только выводы
(«на противоречивой информации BM25 сильнее вектора», «полнота — самое
слабое место: ~35–40% у всех»). Заимствовать его структуру категорий —
разумно; копировать цифры — нет.
